# ADR-001: Mantener Python 3.11 y Flask como stack de aplicación

- **Estado:** Aceptada para el MVP actual.
- **Fecha:** 2026-11-14.
- **Contexto:** GestorTech es una aplicación web para la gestión de reparaciones e inventario de un taller. El proyecto ya está implementado con Python 3.11 y Flask. Utiliza Jinja2 para renderizar las páginas, Blueprints para separar rutas web, autenticación y API, y una organización por capas para separar presentación, aplicación, dominio e infraestructura. La entrega del Módulo 6 busca completar y documentar el MVP, no reconstruirlo con otro framework.
- **Decisión:** Mantener Python 3.11 y Flask. Las páginas web y la API seguirán atendidas por la misma aplicación Flask, conservando la separación interna por módulos y capas.
- **Alternativas consideradas:**
  1. **Django:** ofrece un conjunto amplio de funcionalidades integradas, ORM y administración. No se adopta porque implicaría adaptar una aplicación existente y sumar convenciones y componentes que no son necesarios para el alcance actual.
  2. **FastAPI:** es una alternativa adecuada para construir APIs y ofrece documentación automática. No se adopta porque GestorTech también sirve páginas HTML con Jinja2 y ya dispone de rutas, autenticación y servicios implementados en Flask; cambiar implicaría una reestructuración que no aporta un beneficio necesario para esta entrega.
- **Consecuencias positivas:**
  - Se conserva el trabajo funcional existente y se reduce el riesgo de regresiones por una migración de framework.
  - Se mantiene una única aplicación para las páginas web y los endpoints de API.
  - La separación por capas permite revisar y ampliar responsabilidades sin convertir cada módulo en un servicio independiente.
  - Se evita introducir una migración y dependencias adicionales dentro del alcance del Módulo 6.
- **Costos y limitaciones:**
  - La aplicación debe mantener explícitamente sus convenciones de organización, validación, autenticación y documentación.
  - Si en el futuro se requiere una API independiente o escalar componentes por separado, será necesario evaluar una evolución arquitectónica con evidencia de necesidad.
  - Esta decisión no implica que Flask sea superior a Django o FastAPI en todos los escenarios; responde al estado, alcance y necesidades actuales de GestorTech.
- **Referencias de implementación:** `app/__init__.py`, `app/web/pages.py`, `app/web/api.py`, `app/application/`, `app/domain/` y `app/infrastructure/`.
